# 性能优化总结

## 概述
本文档记录了 `backfill_history.py` 和 `candidate_repository.py` 的性能优化措施。

## 主要优化点

### 1. 批量计算交易日差（backfill_history.py）✅ **已实现**

**问题**：
- **优化前**：`_filter_latest_golden_cross` 函数中对每个候选股票都调用 `calculate_trading_days_diff`，导致多次数据库查询
- **优化前**：`_check_missing_conditions_for_date` 中也存在类似问题，每个候选都单独查询

**优化方案**：
1. **新增 `_batch_calculate_trading_days_diff` 函数**：
   - 批量收集所有需要计算交易日差的日期对 `[(start_date, end_date), ...]`
   - 一次性查询整个日期范围内的所有交易日（一次数据库查询）
   - 使用内存计算所有日期对的交易日差

2. **使用二分查找优化**：
   - 使用 `bisect.bisect_right` 快速定位日期索引
   - 时间复杂度从 O(n) 降低到 O(log n)
   - 避免了对每个日期对的线性搜索

3. **缓存机制**：
   - 批量计算的结果存储在缓存字典中
   - 所有候选共享同一个缓存，避免重复计算

**实现位置**：
- ✅ `_filter_latest_golden_cross`：已实现批量计算和缓存
- ✅ `_check_missing_conditions_for_date`：已实现批量预计算和过滤

**性能提升**：
- **查询次数减少**：假设处理 100 个候选股票，原来需要 100 次数据库查询，现在只需要 **1 次**
- **计算效率提升**：使用二分查找，单次计算时间复杂度从 O(n) 降低到 O(log n)
- **总体性能提升**：预期 **10-50倍**（取决于候选数量）
- **实际效果**：在处理 50-100 个候选时，可将交易日差计算时间从数秒降低到毫秒级

### 2. 缓存交易日列表（backfill_history.py）

**问题**：
- `_get_trading_dates_in_range` 在相同日期范围内被多次调用，重复查询数据库

**优化方案**：
- 添加内存缓存机制，缓存查询结果 1 小时
- 使用缓存键 `{start_date}_{end_date}` 标识不同的日期范围

**性能提升**：
- 对于重复的日期范围查询，直接从内存返回，避免数据库查询
- 预期性能提升：**接近无限**（缓存命中时）

### 3. 优化候选记录查找逻辑（candidate_repository.py）⭐️

**问题**：
- **优化前**：先按 `trade_date` 查询，再按 `golden_cross_date` 查询，造成重复查询
- `_find_existing_record` 中不必要的 `flush()` 操作增加开销
- 查询历史记录时没有使用 `LIMIT 1`
- `_query_by_golden_cross_date` 中使用了不必要的 `order_by`

**优化方案**：
1. **直接确定 `golden_cross_date`**：
   - 如果传入 `golden_cross_date`，直接使用
   - 否则查询历史记录（使用 `LIMIT 1` 优化）
   - 避免先按 `trade_date` 查询的开销

2. **直接使用唯一约束查询**：
   - 完全移除了按 `trade_date` 的查询
   - 直接按 `(ts_code, golden_cross_date)` 查询，利用数据库唯一约束
   - 移除了 `_query_by_golden_cross_date` 中不必要的 `order_by`（唯一约束保证只有一条记录）

3. **移除不必要的操作**：
   - 移除不必要的 `flush()` 调用
   - 优化查询逻辑，减少冗余检查

**性能提升**：
- **查询次数减少**：从 2-3 次降低到 1-2 次（每次 save 操作）
- **查询效率提升**：利用唯一约束索引，查询时间复杂度从 O(n) 降低到 O(1)
- **总体性能提升**：预计 **30-50%**（针对 repository.save 方法）
- **累积效果**：在处理 2880 条记录时，节省约 2880-5760 次查询

### 4. 批量提交事务（backfill_history.py）

**问题**：
- 每个日期处理完后立即提交事务，导致频繁的 commit 操作
- commit 操作是相对昂贵的数据库操作

**优化方案**：
- 改为每 5 个日期提交一次，或在批次结束时提交
- 保持关键点（批次结束、错误恢复）的立即提交

**性能提升**：
- 减少 commit 次数，从每个日期一次降低到每 5 个日期一次
- 预期性能提升：**20-30%**（减少数据库 I/O）

### 5. 预先过滤候选（backfill_history.py）

**问题**：
- 在 `_check_missing_conditions_for_date` 中，对所有候选都获取股票数据，但部分候选可能不符合条件

**优化方案**：
- 预先批量计算交易日差，过滤掉不符合条件的候选
- 只对符合条件的候选获取股票数据

**性能提升**：
- 减少不必要的股票数据获取操作（通常是耗时操作）
- 预期性能提升：**取决于过滤比例，通常 20-40%**

### 6. 批量预检查价格数据（stock_startup_filter.py）⭐️ **关键优化**

**问题**：
- 从日志分析：5000多只股票中，实际只保存了约2880条记录（56%）
- 约44%的股票被过滤，但这些股票仍然进行了完整的指标计算（数据加载、指标计算等）
- 每个股票都调用 `_get_stock_indicators`，即使没有价格数据也会尝试计算

**优化方案**：
- 新增 `_batch_check_price_data_exists` 方法，批量查询哪些股票在指定日期有价格数据
- 在 `batch_filter_startups` 开始时，一次性查询所有股票的价格数据情况
- 只对有价格数据的股票进行指标计算和判断
- 避免对约44%的股票进行不必要的计算

**性能提升**：
- 减少约44%的无效计算（指标计算、数据加载等）
- 预期性能提升：**30-50%**（取决于被过滤股票的比例）
- 特别适用于历史回填场景（数据完整性较好，预过滤效果好）

### 7. 两阶段并行处理优化（stock_startup_filter.py）⭐️ **关键优化**

**问题**：
- `batch_filter_startups` 中每个股票串行处理
- 金叉检查和数据库保存混合在一起，无法充分利用并行计算
- 串行处理导致 CPU 和数据库资源利用率不高

**优化方案**：
采用**两阶段并行处理**架构：

**阶段1：并行检查金叉（只计算，不保存数据库）**
- 使用 `ThreadPoolExecutor` 并行处理所有股票
- 调用 `check_golden_cross_only` 方法，只进行金叉计算，不保存数据库
- 此阶段完全并行，无数据库写操作，可以充分利用 CPU 多核

**阶段2：串行处理有金叉的股票（检查条件、保存数据库）**
- 对阶段1发现的有金叉的股票，串行处理
- 保存金叉记录，然后检查核心条件、辅助条件、风险条件
- 此阶段涉及数据库写操作，串行处理避免并发冲突

**实现细节**：
- 新增 `check_golden_cross_only` 方法：只检查金叉，不保存数据库
- 新增 `_check_golden_cross_only` 方法：处理单个股票的金叉检查
- 新增 `_process_stock_with_golden_cross` 方法：处理有金叉的股票的条件检查
- 自动控制并发数量：
  - 默认：使用 CPU 核心数，但不超过 16（避免资源耗尽）
  - 可通过 `max_workers` 参数手动控制（0或1表示串行处理）

**性能提升**：
- **阶段1并行优势**：
  - 金叉检查是 CPU 密集型操作（指标计算、条件判断）
  - 不涉及数据库写操作，完全并行无锁冲突
  - 可以充分利用多核 CPU，性能提升接近线性
  
- **总体性能提升**：
  - 假设 5000 只股票，其中 2800 只有金叉
  - 阶段1：2800 个并行计算任务（假设 8 核），时间从 2800*T 降低到 350*T（约 8 倍）
  - 阶段2：2800 个串行任务，时间不变
  - **总体性能提升：预计 4-8倍**（取决于有金叉股票比例和 CPU 核心数）

**注意事项**：
- **数据库连接池**：阶段1不需要数据库连接，阶段2串行处理，对连接池要求较低
- **内存使用**：阶段1会缓存所有股票的数据，内存使用会有所增加
- **错误处理**：每个线程的错误独立处理，不影响其他线程

**保存时机说明**：
- **阶段1（并行）**：只计算金叉，**不保存数据库**
- **阶段2（串行）**：对有金叉的股票，在 `_process_stock_with_golden_cross` 方法中：
  1. **先保存金叉记录**（第246行）：调用 `repository.save` 保存金叉候选（20分，stage='golden_cross'）
  2. **然后检查其他条件**（第262行）：调用 `check_conditions` 检查核心/辅助/风险条件
  3. **更新记录**：`check_conditions` 会根据 `golden_cross_date` 查找刚才保存的记录并更新
     - 如果条件满足，记录会被更新为更高的分数和阶段（confirmed 或 started）
     - 如果条件不满足，记录保持为 golden_cross 阶段（20分）

**数据流程**：
```
阶段1（并行）：
  5000只股票 → 并行计算金叉 → 发现2800只金叉（内存中，未保存）

阶段2（串行）：
  2800只有金叉的股票 → 逐个处理：
    → 保存金叉记录（20分）→ 数据库写入
    → 检查核心条件 → 更新记录（如果通过）
    → 检查辅助条件 → 更新记录（如果通过）
    → 检查风险条件 → 更新记录（如果通过，最终100分）
```

**使用示例**：
```python
# 默认：自动两阶段并行处理（阶段1并行，阶段2串行）
result_df = filter_service.batch_filter_startups(stock_codes, trade_date)

# 指定阶段1的并发数
result_df = filter_service.batch_filter_startups(stock_codes, trade_date, max_workers=8)

# 禁用并行（串行处理，兼容旧版本）
result_df = filter_service.batch_filter_startups(stock_codes, trade_date, max_workers=1)
```

### 8. 优化日志输出（stock_startup_filter.py）

**问题**：
- `batch_filter_startups` 处理大量股票时，每个股票都可能产生日志，导致日志开销

**优化方案**：
- 减少日志频率，每处理 500 个股票记录一次进度
- 使用 DEBUG 级别记录进度信息
- 记录预过滤统计信息

**性能提升**：
- 减少 I/O 开销（日志写入）
- 预期性能提升：**5-10%**

## 当前性能瓶颈分析

根据日志分析（处理约5000只股票，30-60秒）：

### 主要瓶颈1：指标计算开销（已优化 ✅）
- **问题**：对没有价格数据的股票也进行完整的指标计算
- **影响**：约 44% 的股票（2200只）进行了无效计算
- **耗时**：估计占总时间的 20-30%
- **状态**：已通过批量预检查优化

### 主要瓶颈2：数据库会话开销（待优化）
- **问题**：每个股票都调用 `repository.save`，创建独立 session 并立即 commit
- **影响**：约 2880 次独立的数据库会话和提交操作
- **耗时**：估计占总时间的 60-70%
- **状态**：待实现批量保存机制

### 进一步优化建议

#### 方案1：批量保存（推荐，但需要较大重构）
1. 收集所有需要保存的记录（暂不调用 `repository.save`）
2. 批量查询所有 existing 记录（一次查询）
3. 使用 `bulk_insert_mappings` 和 `bulk_update_mappings` 批量操作
4. 批量提交（每 500-1000 条记录提交一次）

**预期性能提升**：**5-10倍**（从 30-60秒降低到 3-10秒）

**实现难度**：高（需要重构 repository.save 的逻辑）

#### 方案2：共享 Session（中等难度）
1. 在 `batch_filter_startups` 中创建一个共享 session
2. 修改 `repository.save` 支持传入外部 session
3. 每处理 500-1000 个股票提交一次

**预期性能提升**：**2-3倍**（减少 session 创建开销）

**实现难度**：中（需要修改 repository 接口）

#### 方案3：并行处理（✅ 已实现）
1. 使用 `ThreadPoolExecutor` 并行处理多个股票
2. 自动控制并发数量（默认不超过 CPU 核心数，最大16）
3. 每个线程使用独立的 session（`repository.save` 内部创建）

**预期性能提升**：**2-4倍**（取决于 CPU 核心数和数据库连接池大小）

**实现难度**：中（已实现，默认启用）

**注意事项**：
- 需要确保数据库连接池大小足够（建议 >= max_workers * 2）
- 每个线程会创建独立的数据库 session，内存使用会略有增加
- 可以通过 `max_workers` 参数控制并发数（0或1表示串行处理）

## 优化效果估算

假设处理 100 个候选股票，20 个交易日：

### 优化前：
- 交易日差计算：100 × 20 = 2000 次数据库查询
- 事务提交：20 次
- 不必要的股票数据获取：假设 30% 不需要，即 600 次多余操作

### 优化后：
- 交易日差计算：20 次批量查询（每天一次批量）
- 事务提交：4 次（每 5 个日期一次）
- 不必要的股票数据获取：0 次（已预先过滤）

### 总体性能提升估算：

#### 已实现的优化：
- **数据库查询减少：99%**（从 2000+ 次降低到 20+ 次）
- **事务提交减少：80%**（从 20 次降低到 4 次）
- **无效计算减少：44%**（预过滤没有价格数据的股票）
- **当前总体性能提升：预计 2.5-4 倍**（已实现的优化）

#### 预期性能提升（处理后）：
- 从 30-60秒降低到 **5-10秒**（假设处理5000只股票，保存2880条，8核CPU）
  - 批量预检查：节省约 10-15秒（44%无效计算）
  - 两阶段并行处理：节省约 15-25秒（阶段1并行加速 4-8倍）
  - 批量交易日差计算：节省约 5-10秒
  - 其他优化：节省约 5秒

#### 潜在性能提升（如果实现批量保存）：
- **5-10倍**（从 15-25秒降低到 3-5秒）

## 注意事项

1. **内存使用**：批量计算和缓存会增加内存使用，但对于正常规模的回填任务影响很小
2. **缓存失效**：交易日列表缓存会在一小时后自动失效，确保数据新鲜度
3. **兼容性**：所有优化都保持向后兼容，不影响现有功能
4. **错误处理**：优化后的代码保留了原有的错误处理和降级逻辑
