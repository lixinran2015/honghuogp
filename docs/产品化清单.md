---

## 二、缺口一览（按优先级）

### 🔴 必须补（上线/对外前）

| 序号 | 项目 | 说明 | 建议做法 |
|------|------|------|----------|
| 1 | **身份与访问** | 当前无登录、无鉴权，API 完全开放 | 增加登录（含前端登录页 + 后端 JWT/Session），关键 API 加鉴权中间件；若仅内网使用可先做 IP/简单 Token 白名单 |
| 2 | **配置与密钥不入库** | `config.json` 含 API Key，若进仓库有泄露风险 | 敏感项改为环境变量（如 `DEEPSEEK_API_KEY`、`TUSHARE_TOKEN`），`config.json` 只保留非敏感或提供 `config.json.example` |
| 3 | **生产环境配置** | 前端多处写死 `localhost:8000`，生产需指到真实后端 | 构建/运行用 `VITE_API_BASE_URL`，部署文档中明确生产值；可考虑前端单点 axios baseURL，减少散落写死 |
| 4 | **README 与部署说明** | README 仍是 Streamlit，实际为 Vue + FastAPI | 更新 README：技术栈（Vue3 + FastAPI）、本地开发、环境变量、数据库要求；单独写「生产部署」：构建、进程管理、反向代理（如 Nginx）、HTTPS |

### 🟡 建议补（体验与可运维）

| 序号 | 项目 | 说明 | 建议做法 |
|------|------|------|----------|
| 5 | **容器化部署** | 无 Docker，生产环境一致性差 | 增加 `Dockerfile`（后端）、前端构建后由 Nginx 镜像或同一 compose 提供；`docker-compose.yml` 含后端 + 前端 + PostgreSQL（若适用） |
| 6 | **统一错误与空状态** | 接口失败/无数据时，前端表现不统一 | 全局 axios 响应拦截：统一弹 toast/提示；列表页统一「加载中 / 无数据 / 错误」占位与文案 |
| 7 | **健康检查可观测** | 仅有 `/api/health` 返回 ok，无依赖状态 | 健康接口内增加 DB 连接、关键外部依赖（如 Tushare 可用性）检测，返回 503 + 原因；便于监控/告警 |
| 8 | **API 限流与防护** | 接口无限流，易被刷或误伤 | 对登录、AI 诊断、爬虫相关等接口做限流（如按 IP 或按用户）；可先用 in-memory，后续再上 Redis |
| 9 | **操作可追溯** | 敏感操作（如删除、批量执行）无记录 | 关键操作写审计日志（谁、何时、做了什么、结果）；可先落库或写文件，后续接审计查询页 |

### 🟢 可选（体验与长期维护）

| 序号 | 项目 | 说明 | 建议做法 |
|------|------|------|----------|
| 10 | **前端单点 baseURL** | 多个页面重复定义 `API_BASE_URL` | 抽成 `api/client.js` 或 axios 实例，统一 `baseURL` 与拦截器，页面只引用该实例 |
| 11 | **错误监控** | 仅文件日志，生产问题难追踪 | 接入 Sentry（或类似）用于前端 + 后端异常上报与统计 |
| 12 | **用户手册 / 帮助** | 无面向最终用户的使用说明 | 在「知识库」或帮助中心增加：功能导览、常见问题、数据更新说明；可复用现有知识库文档结构 |
| 13 | **合规与免责** | 若对外提供投资相关能力 | 登录后首次使用提示、免责声明；必要时增加简单的隐私条款/使用条款页（可静态） |

## 三、实施顺序建议

1. **先做**：配置与密钥环境变量化（2） + 生产 API 地址与部署文档（3）（4）  
   → 不改变功能，只提升安全与可部署性。  
2. **再做**：身份与访问（1）  
   → 按「内网/公网、单用户/多用户」选最小方案（如单用户 + 简单密码 + JWT）。  
3. **随后**：容器化（5）、统一错误与空状态（6）、健康检查增强（7）  
   → 提升部署一致性和可观测性。  
4. **按需**：限流（8）、审计（9）、前端 baseURL 收敛（10）、监控与帮助（11）（12）（13）。

---

## 四、小结

- **当前最缺**：**身份与访问控制**、**配置/密钥不入库**、**生产部署与文档**、**统一错误与空状态**。  
- 补上「必须」四项后，即可在受控环境下做小范围或内网产品化上线；再按「建议」和「可选」逐步完善体验与运维能力。

如需对某一项做具体实现方案（例如登录流程、Docker 目录结构、Nginx 配置示例），可以指定序号或名称继续细化。
